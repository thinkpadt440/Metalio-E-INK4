# Metalio E-Ink4 设备端功能实现计划

真实后端接入在 feature/companion 执行；feature/dashboard 暂用于脱机演示，见 [演示指南](offline-demo-guide.md)。本计划后续以 companion 中保留的开发基线为准。

本计划以 [接口约定 v1](device-harness-api-v1.md) 和 [完整报文示例 v1](device-harness-api-v1-examples.md) 为唯一协议依据，覆盖 Dashboard、Session/消息、模型和授权、BOOT 录音上传、实时任务、审批与断线恢复。实现按下列顺序逐阶段验收；接口变更先更新协议文档，再改固件。

## 当前基线

- 固件基于官方 2.0.63，目标板 Metalio E-Ink4 / ESP32-S3，UI 逻辑尺寸 480×800 竖屏。
- 当前分支已有 Dashboard 和助手示例 UI、BOOT 本地录音，以及 HTTP/WebSocket 底层能力。
- Dashboard 数据、Session/模型/授权和聊天内容目前是本地示例。录音保存在 PSRAM，尚未上传；第二次录音可覆盖上一次。
- Harness WebSocket 客户端、录音接受确认、真实历史/任务/审批和在线恢复尚未接入。自动空闲/待机时网络可能被电源策略关闭。
- 本计划只规定后续工作，不表示上述能力已实现或已在真机验证。

## 实现边界与安全规则

1. 优先新增隔离的 Harness 应用层代码（建议 main/harness/），统一处理 HTTP、WS、协议对象、业务状态和录音提交。LVGL 回调只发起请求/更新页面，不等待网络；网络任务不直接操作 LVGL。
2. 复用现有 NetworkInterface 的 HTTP/WebSocket 工厂和 AudioService。通用 WebSocket 库、AudioService、PowerPolicy 和板级文件属于共享底层，只有相应阶段必须修改时才动，每次保留现有默认行为并加入回归验证。
3. WebSocket 现有默认接收单帧上限为 2048 字节。保持其他应用默认值不变；Harness 连接单独设为至少 8192 字节。必须同时实现每连接独立的分片状态、完整消息 8192 字节上限、TCP 拆包/合包处理、连接重置清理和带长度的 JSON 解析。只调用 SetReceiveBufferSize(8192) 不算完成。
4. PCM 上限是 30 秒、约 1.92MB。不得把 PSRAM 裸指针暴露给网络层，也不要再复制一份完整 PCM 到内部 RAM；通过 AudioService 的锁保护分块读取。服务端尚未确认 accepted 时，录音缓冲不能被新录音覆盖。
5. 不改音频采样格式/硬件引脚、显示驱动/旋转、分区表、原有 WebSocket 默认上限、配网凭据或通用睡眠策略的默认行为。若必须改共享电源策略，新增明确、可释放的 Harness 在线需求并验证待机唤醒及旧场景。
6. 不撤销或覆盖当前分支已有的 Dashboard、助手 UI 和 UI 预览改动。每阶段只改必要文件并审查 diff；提交、推送或刷机不包含在本计划内。

## 分阶段路线

### 阶段 0：基线与构建门禁

**工作：**记录当前 Git 工作区差异；确认 WSL 的 ESP-IDF 环境、完整构建和 UI 离线预览都可运行。保留现有未提交改动。后端地址和端口沿用协议文档的配置约定，真实地址由后端交付，不猜测 SSH 地址就是服务地址。

**验收：**能够复现当前构建；预览工具可启动；保存当前已有失败/告警基线。若基线构建失败，先定位是本分支已有问题还是环境问题，不把它带入网络适配阶段。

### 阶段 1：WebSocket 接收安全补强

**工作：**先为帧/消息解码建立主机侧测试，再最小化修改 components/esp-ml307 WebSocket 接收代码。把分片累积状态从函数静态变量移到 WebSocket 实例；限制帧与重组后消息大小；应答 Ping、处理 Close；清理断线/重连状态；避免把接收缓冲长度误当 C 字符串长度。Harness 创建连接时，在 Connect 前设置 8192 字节单帧上限，其他旧客户端仍使用默认 2048 字节。

**测试：**2048 字节以下旧消息；2048–8192 字节 JSON；超过上限拒绝；帧头/负载在任意 TCP 回调边界拆分、多个帧合并回调、continuation 重组、中途中断后重连；两个 WebSocket 实例交错收包互不串数据。保留原 XiaoZhi WebSocket 行为的构建回归。

**验收：**边界条件有自动测试；固件构建通过；默认上限未被全局抬高。任一不稳定则不进入业务协议开发。

### 阶段 2：Harness 客户端与连接/同步

**工作：**新增独立客户端，使用固定 Demo 服务地址、X-Device-ID 且不带 Authorization。HTTP 统一校验状态码/响应长度并设置超时。WS 实现 hello、连接 ID、心跳、命令 ID、ack 超时、重连退避和事件队列。按 hello → GET /sync 分页 → sync.complete → 缓存事件回放 → sync.ready 顺序恢复；ready 前不接受录音、审批或取消操作。

**测试：**用依据报文示例制作的本地模拟服务覆盖正常连接、无服务、握手失败、超时、半包/超长消息、同步多页、同步过期、快速断线和重连。连续重试不得创建重复任务或阻塞 UI。

**验收：**设备能稳定连接并同步空状态；连接状态能显示在助手标题；等待网络期间页面和按键仍可用。

### 阶段 3：Dashboard、Session 目录与配置

**工作：**接入 GET /dashboard/overview，周期切换时请求 all/30d/7d，按文档约定刷新；把模型、授权目录和最近 Session 列表替换为真实数据。固定闲聊用 PUT default-casual-session；进入会话时 GET Session。模型/授权选择后按 expected_settings_version 调 PATCH settings，冲突时刷新服务端配置，不在设备端伪造成功。

**测试：**空目录、不可用默认值、长名称/中文、列表游标、HTTP 错误、设置冲突、重复选择同一值和多个 Session 使用不同设置。

**验收：**Dashboard 数值真实且空值正确显示；所选 Session、固定闲聊及每会话配置相互独立，切换/重进后与服务器一致。

### 阶段 4：聊天历史、显示分页与流式合并

**工作：**进入会话后用 GET /sessions/{id}/messages 先加载最新内容。将网络消息放入有界缓存，再按 480×800 正文区域排版：音量键/盖板虚拟键翻本地屏幕页，到缓存旧端才用 before_cursor 加载更早内容。长消息按 UTF-8 字节偏移拼接，不截断字符；保留 message_id 和绝对字节偏移。接入 message.delta/completed，按 message_id+offset 去重；用户在旧页时不抢页，只显示新消息提示。同步边界出现缺口则从 Session 消息接口补读。

**测试：**空会话、长文本跨多屏、长消息续取、中文/emoji 边界、历史与 WS 重复/乱序片段、旧记录翻页时新消息到达、缓存回收后继续读旧消息、页面频繁切换与资源释放。

**验收：**消息不丢字节、不重复、不串 Session；内存使用有界；LVGL 对象不随历史总量无限增长；长时间任务输出不逐 token 刷屏。

### 阶段 5：BOOT 录音上传与接受确认

**工作：**扩展 AudioService 的受锁分块读取接口，不交出底层 PCM 指针。长按开始前锁定目标 Session/settings_version；松开后冻结 PCM 和 utterance_id，自动发 audio.begin，按 ≤4096 字节发送原始 PCM Binary，再发 audio.end。界面显示录音/发送/重试/已接受状态。每段未确认录音只保留一份；阻止第二段录音覆盖它。仅收到匹配 utterance_id 的 accepted 和 run_id 后释放 PSRAM 缓冲，不等 ASR/智能体完成。

**失败恢复：**网络中断或 ack 丢失时保留 PCM 和原 utterance_id；重连先用新 command_id 重发 begin，由服务端去重确认是否已接受。若服务端仍要求上传，则从头重传。收到 busy/settings_conflict 时提示用户；明确放弃录音前解释服务端可能已接受但确认丢失，不能把放弃本地 PCM 表现成取消任务。RAM 录音在掉电后无法恢复，不显示“已发送”。

**测试：**音频 SHA-256、长度/时长校验、首尾块/奇数字节拒绝、上传中断、begin/end ack 丢失、同 utterance 重试、被网页任务抢占、改配置、空录音、30 秒上限、服务端接受后不重复创建 run。

**验收：**完整路径为 BOOT → 本地 PCM → 自动上传 → accepted/run_id → asr.final 文本回显 → 智能体事件。前述失败注入均不静默丢录音或重复执行。

### 阶段 6：任务状态、进度、取消与重启恢复

**工作：**消费 run.accepted/state/progress/completed/failed/cancelled；按对象版本忽略旧事件。长任务进度合并显示。任务回复继续通过 message.delta/completed 展示。断线后按同步快照恢复活动 run；曾追踪但不在快照中的 run 用 GET /runs/{id} 查询终态。按文档实现 run.cancel 命令和状态处理；提供明确的取消入口且不占用聊天页底部模型/授权位置，取消不回滚已完成工具操作。

**测试：**长任务切页/重连、事件重放、旧版本、最终事件丢失、服务端已结束、取消与完成竞争、取消不支持、网页发起的任务，以及同 Session 并发 busy。

**验收：**断线不取消服务器任务；恢复后设备状态与服务端一致；不因重复事件重复显示/执行。

### 阶段 7：审批状态机与墨水屏界面

**工作：**处理 approval.requested/resolved，并支持 GET /approvals/{id} 查询。当前 Session 的审批在聊天中提示并进入审批详情子页，显示原因、工具与完整操作；长内容用音量键/盖板键分页。底部临时显示“仅本次允许/拒绝”，保留原聊天位置，处理后回到会话。BOOT 在审批页禁用录音。非当前 Session 只显示可点击提醒，不强制跳页。单次提交中禁用按钮；以服务器返回的状态为准。

**安全规则：**按 approval_id + expected_approval_version 唯一决定；服务端拒绝批准、过期、网页抢先决定和当前版本冲突时显示真实最新对象。operation 不可在 ≤8192 字节内完整传输时设备不得显示“允许”，提示去 Harness 网页处理；拒绝仍可用。授权级别变更不自动批准既有审批。

**测试：**允许一次、拒绝、过期、取消、网页竞争、重复按键、断网、超长操作、多个 Session 审批、任务取消与审批同时到达。

**验收：**批准前工具未执行；每个审批最多一个最终决定；界面从不让用户批准被截断/不可读的操作。

### 阶段 8：电源策略、整机联调与交付

**工作：**先实测当前空闲、助手页面、待机页和浅睡下 Wi-Fi/WS 状态，再设计最小的 Harness 在线电源需求。默认电源策略维持原样；仅在 Harness Demo 需要在线时持有新需求，并保证所有离开/错误路径都释放。按照协议目标验证 Dashboard/待机下的在线行为；如果板级浅睡确实无法保 WS，明确选择在线待机或唤醒后同步，不静默牺牲续航或通知能力。

**整机回归：**Dashboard、Session 选择/闲聊、模型授权、长历史、录音确认、ASR 回显、长任务、审批、断网/后端重启、应用重启、空闲/待机/唤醒、音量/BOOT/POWER、真实墨水屏刷新。完整 ESP-IDF 构建和 UI 主机预览均通过后再进行真机烧录。

**验收：**端到端测试按两份协议示例核对每个 ID、状态、字段长度与时序；原始按键、麦克风、屏幕刷新、USB/WSL 烧录及网络待机都有真机记录。静态示例和主机模拟不能代替真机验收。

## Codex 执行方式

未来按阶段顺序逐步实施，每次只处理一个可独立验收的阶段。Codex 可负责源码检查/修改、主机侧协议与状态机测试、UI 离线预览、ESP-IDF 构建和 diff 审查；真实麦克风、屏幕波形、网络覆盖和电源待机仍需在设备及后端可用时验证。涉及共享底层时先写回归测试，再改最小范围；构建/测试失败先修复，不把失败带到后续阶段。阶段完成时汇报改动文件、测试结果、未验证项，再开始下一阶段。
